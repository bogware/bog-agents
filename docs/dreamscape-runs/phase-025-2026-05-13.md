# Phase 25 — 2026-05-13 (production telemetry infrastructure)

Twenty-fifth real-world pass. The campaign's effectiveness
measurements (Phases 10-22) have all been **offline**: scripted
scenarios, blind A/B with a Sonnet judge, aggregated win rates.
That's a good proxy for "does dreamscape help on the prompts I
expect" — it can't answer "does dreamscape help my real users on
their real work."

Phase 25 ships the infrastructure for the second question. **No
new effectiveness measurement** — just the plumbing that makes
future production data collection possible.

## TL;DR

* **New module** `bog_agents_cli/dreamscape/telemetry.py` (~240 lines)
  with `record_event`, `iter_events`, `aggregate_events`,
  `clear_telemetry`.
* **Event log** at `~/.bog-agents/agents/<id>/telemetry.jsonl`,
  append-only, rotated at 1 MB.
* **Three event kinds:** `dream_fired`, `injection_fired`,
  `injection_helped`. Wired into `maybe_dream` +
  `ImaginationMiddleware._maybe_inject` + `_record_outcome`.
* **`/dreamscape stats [H|all]`** slash command surfaces the
  aggregated view: counts, helped-rate, dreams-by-category,
  injections-by-style, approx LLM cost.
* **10 new unit tests** cover record/iter/filter/aggregate/render.
* **Live demo** confirms the full pipeline end-to-end with real
  Haiku-fired dreams + mechanism-only injections.

## What gets logged

Per dream:
```jsonl
{"ts": ..., "kind": "dream_fired", "agent_id": "myagent",
 "metadata": {"title": "...", "elapsed_seconds": 6.2,
              "seeds_used_count": 2, "category": "engineering-craft"}}
```

Per injection:
```jsonl
{"ts": ..., "kind": "injection_fired", "agent_id": "myagent",
 "metadata": {"injection_style": "neutral",
              "content_category": null, "excerpt_count": 2}}
```

Per helped:
```jsonl
{"ts": ..., "kind": "injection_helped", "agent_id": "myagent",
 "metadata": {}}
```

The `injection_helped` event fires from `_record_outcome` when the
response immediately following an injection is non-error (no
"Traceback", "Error:", "Exception:", etc. markers). It's the same
signal that drives `imagination_injections_helped` on the snapshot
+ the auto-disable threshold — now made visible.

```

  Window: all time
  Total events:       6
  Dreams fired:       2
  Injections fired:   2
  Injection helped:   2/2 (100% success rate)
  Approx LLM cost:    $0.0020

Dreams by category
  nature                 2

Injections by style
  neutral                2
```

In a real production session, the breakdowns would show what
dreamscape is actually doing for the user: which seed categories
dominate (a routed engineering agent should see ~all
`engineering-craft`), which wrappers fire most (creative agents
get `dreams`, engineering get `neutral`), and how often the
injection precedes a non-error response.

## What this unlocks

* **`/dreamscape stats`** as an operator surface. Users can run it
  mid-session to see what dreamscape is doing for them.
* **Future Phase 28+ analysis.** Once telemetry accumulates across
  real deployments, the question "do real users get helped by
  dreamscape" becomes answerable from data, not just judge proxies.
* **Sanity checking the routing.** An engineering agent whose
  `dreams_by_category` shows mostly "myth" would indicate a
  classification bug. Telemetry makes those errors visible.
* **Cost transparency.** `approx_cost_usd` lets users see what
  background dreaming actually costs them — the bog-agents-daemon
  could even surface it in a status line.

Phase 25 itself is infrastructure work. The cost is unit tests + a
small demo. Real deployment cost is what accumulates from real
usage — and that's bounded by the existing `max_dreams_per_day`
cap from Phase 3.

## Verdict

**READY TO MERGE.** Clean infrastructure landing — no effectiveness
claim, just the plumbing. The campaign's offline measurements are
unchanged. The data accumulates as users use dreamscape; future
research can answer questions the offline judge proxy can't.

## Next steps

* **Phase 28 (suggested):** privacy-respecting telemetry exporter.
  Operators who want to aggregate across deployments would need a
  way to push the JSONL to local-file / S3 / SQLite. The default
  stays local-only.
* **Phase 29 (suggested):** re-validate the campaign's offline
  findings against real production telemetry once it accumulates.
  Real-user signals might disagree with the Sonnet judge — that
  disagreement is itself informative.
* **Phase 30 (suggested):** richer feedback signals beyond
  keyword-failure-detection. Did the user explicitly thank the
  agent? Edit the suggested code without rejecting it? Accept a
  tool call without further prompting? Each of these is a stronger
  signal than "response didn't say traceback."
