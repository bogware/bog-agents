# Phase 7 — 2026-05-13 (daemon-style runner + cross-process continuity)

Seventh real-world pass. **The "survives process death" milestone.**
Phases 3 + 5 proved the scheduler works across multiple cycles and
multiple agents within a single process. Phase 7 proves that a fresh
process can pick up exactly where the prior process left off — the
property you need before you can run dreamscape under systemd /
Windows Task Scheduler / `bog-agents-daemon`.

## TL;DR

**The dream cycle survives process death.** All the durable state
(snapshots + dream archive) lives on disk; the runner is just the
shape that keeps the asyncio task alive between snapshot writes.

## The new module

`bog_agents_cli/dreamscape/runner.py` is a small, standalone CLI:

```bash
python -m bog_agents_cli.dreamscape.runner \
    --agent-id myagent \
    --model anthropic:claude-haiku-4-5
```

Key design points:

* **Resumes existing snapshot.** First thing the runner does is read
  `~/.bog-agents/agents/<agent_id>/lifecycle.json`. If it exists, the
  imagination trait and dream archive are preserved — the runner never
  zeroes them. This is the invariant the unit test
  `test_resumes_existing_snapshot_without_resetting` pins.
* **Seeds fresh on first run.** If there's no snapshot yet, the runner
  writes one with a backdated `last_activity_at` so the first tick
  sees `DORMANT` immediately. (Otherwise a brand-new agent would have
  to wait the full dormancy window before any dream could fire.)
* **Cross-platform signal handling.** SIGINT + SIGTERM on POSIX;
  Ctrl-Break on Windows. The runner stops the scheduler cleanly and
  persists final state on either.
* **Optional duration.** `--duration-seconds N` for finite test runs;
  default is indefinite (run until signal).

## Live test — 5 process invocations

```
agent_id = "phase7-cross-proc"
poll = 3 s    dormancy = 4 s    dreaming = 2 s
```

| Run | Elapsed | rc | Dreams before → after | Imagination before → after | Notes |
|---|---|---|---|---|---|
| A — fresh start | 32.2 s | 0 | 0 → 3 | 0.00 → 0.03 | first-ever process for this agent_id |
| B — continuation | 32.3 s | 0 | 3 → 6 | 0.03 → 0.06 | second process, same agent_id |
| C — third process | 17.3 s | 0 | 6 → 8 | 0.06 → 0.08 | confirms cadence holds across N processes |
| D — SIGKILL | n/a | 1 | (killed at ~8 s) | snapshot held at 0.08 | abrupt termination, no graceful shutdown |
| E — post-crash | ~15 s | 0 | 8 → 10 | 0.08 → 0.10 | snapshot still readable, new dreams stack |

All five processes accumulated state cleanly. Imagination went
**0.00 → 0.03 → 0.06 → 0.08 → 0.08 → 0.10** — monotonic across every
process boundary, no resets, no double-counts.

## Crash-recovery specifics

Run D was killed via `subprocess.Popen.kill()` — which on Windows
sends `TerminateProcess`, the rough equivalent of SIGKILL. The
runner had no chance to clean up. Yet:

1. The snapshot on disk was still readable after the crash.
2. Run E started fresh, read that snapshot, and saw `imagination=0.08`
   (the post-D value, not zero).
3. Run E produced 2 more dreams on top of the existing 8.

So a hard crash *during* a write would still leave the snapshot in
a consistent state — that's `LifecycleSnapshot.save_snapshot`'s atomic
write doing its job. Good defensive shape.

## Wave 4 implications

The dreamscape runner is now production-deployable as a long-running
service. To make it actually run under `bog-agents-daemon`, the
minimal lift is a daemon job-type that invokes `python -m
bog_agents_cli.dreamscape.runner` on startup and supervises it like
any other systemd unit — no further dreamscape-side code changes
needed. The daemon already has cron + interval + webhook triggers; a
daemon job could even start/stop the dreamscape runner on a schedule
(e.g. only dream during off-hours).
