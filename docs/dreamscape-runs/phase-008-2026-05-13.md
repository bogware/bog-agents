# Phase 8 — 2026-05-13 (automation: trends.md from JSON snapshots)

Eighth real-world pass. **The meta-phase.** By Phase 7, `trends.md`
was 100+ lines spanning five tables, all hand-maintained. Every time
a new phase landed, I had to manually edit five tables, and the
likelihood of drift was rising. Phase 8 closes that loop.

## TL;DR

* Built `scripts/build_dreamscape_trends.py` — a 555-line Python
  tool that reads every `phase-*.json`, normalizes the heterogeneous
  shapes (P1-P2's scenarios array vs P3-P7's flatter
  `live_test.results`), and re-renders the cross-phase tables.
* **Idempotent.** Running it twice produces no diff.
* `--check` mode for CI: exits non-zero if `trends.md` is stale.
* **5 new unit tests** cover load + render + check + the two
  divergent JSON shapes.
* Back-filled `test_suite_stats` to phases 3-7 + `test_focus` to
  phases 1-2 so the auto-generated trend tables are complete.
* `trends.md` is now sourced from the JSONs — if a new phase lands,
  drop in a new JSON snapshot and run the script.

## Why this matters

The previous `trends.md` had a quiet liability: the tables were
copy-edited manually each phase, and the *truth* (per-phase JSON
snapshots) lived elsewhere. If the JSON and the table disagreed,
you'd have to read both to figure out which one was wrong.

Phase 8 inverts the relationship: the JSONs are the single source
of truth; the table is a view over them. Drift is no longer
possible — you can re-render at any time and confirm.

This is exactly the same shape as the constitution + laws files
sitting in the dreamscape itself: the rules live in `.md` files,
the runtime reads them, and the dashboard renders what's actually
loaded. Single source of truth, derived views downstream.

## The generator's design

```
scripts/build_dreamscape_trends.py
├── PhaseSummary dataclass     # normalized record, every field optional
├── extract_summary(blob)      # heterogeneous JSON → PhaseSummary
├── render_markdown(summaries) # PhaseSummary list → trends.md content
├── load_phase_summaries()     # disk → list[PhaseSummary]
└── main()                     # CLI: regenerate or --check
```

Key design decisions:

1. **Every field on `PhaseSummary` is optional.** The P1 JSON has a
   `scenarios` array; P3+ has `live_test.results`. The normalizer
   pulls whichever exists and falls back to `None`. Missing fields
   render as `n/a` in the table.
2. **No silent drift.** The `--check` mode is the CI invariant: if
   the on-disk `trends.md` doesn't byte-match the rendered output,
   exit 1.
3. **Use the real JSONs as test fixtures.** The unit tests load the
   actual on-disk phase-NNN-*.json files instead of synthetic
   blobs — they're the contract the script promises to handle.
   Synthetic tests verify the two divergent JSON shapes (scenarios
   vs live_test) round-trip correctly.

## Back-fills applied

To make the auto-generated trend tables complete, I patched in two
small fields:

* **`test_suite_stats`** added to phase-003 through phase-007.
  Earlier the unit-test count column only had data for Phase 2.
  Now the cumulative growth (30 → 37 → 42 → 43 → 43 → 43 → 47 → 52)
  is visible in one row.
* **`test_focus`** added to phase-001 and phase-002. Earlier those
  phases had no top-level focus string, so the auto-generated phase
  log just said "(no focus recorded)". Now every line in the phase
  log carries a one-sentence summary.

These back-fills are *data* changes, not test re-runs — the original
phase data and verdicts are unchanged.
