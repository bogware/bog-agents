# Phase 4 — 2026-05-13 (imagination injection live test)

Fourth real-world dreamscape pass. **Found a real bug.** Until today,
the imagination middleware was silently broken — the injection path
called `append_to_system_message(request, body)` instead of
`append_to_system_message(request.system_message, body)`, so every
attempted injection raised `AttributeError: ModelRequest has no
attribute 'content_blocks'` and was swallowed by the surrounding
try/except. The feature has scored 🟢 "sings" since Phase 1, but
no test ever drove the injection path end-to-end.

## TL;DR

* **Bug found + fixed**: `imagination.py:170` was passing the wrong
  type to the SDK helper. One-line fix + regression test added.
* **Mechanism verified**: injection header now lands in
  `request.system_message`, dream excerpts appear in the prompt
  (1304-char post-injection prompt vs 12-char base).
* **Live A/B against Haiku 4.5**: with the same stuck-permission
  question, treatment response diverged meaningfully from control —
  treatment opened with "step back from the file itself" + emphasized
  the directory hierarchy, while control dove straight into mount
  flags and SELinux.
* **Auto-disable verified**: when injection success rate dipped below
  40%, the middleware silently skipped.
* **No dream-vocabulary leakage**: the model treated the injected
  excerpts as raw material, not factual context — zero dream-words
  appeared in either response.

## The bug

```python
# Before (broken — silently swallowed):
new_request = append_to_system_message(request, body)

# After:
new_system = append_to_system_message(request.system_message, body)
new_request = request.override(system_message=new_system)
```

The SDK helper signature is
`append_to_system_message(system_message: SystemMessage | None, text: str) -> SystemMessage` —
it reads `.content_blocks` off the first argument. Passing the whole
`ModelRequest` raised `AttributeError`, which the `except Exception`
in `_maybe_inject` (intentionally there to never raise into the
prompt path) caught and logged. The snapshot counter never
incremented, the model never saw the injection. The slow leak: zero
test exercised the actual injection flow.

**Phase 1 said "imagination injection sings."** What that actually
meant was: the gating logic returned True at the right times. The
gating was correct. The execution was orphan. This is the lesson —
*verdict by mechanism is necessary but not sufficient; verdict by
behavior requires driving the whole pipeline.*

## Live A/B test

| | Control | Treatment |
|---|---|---|
| Model | Haiku 4.5 | Haiku 4.5 |
| Prompt | same | same |
| System prompt | 32 chars | 1358 chars (1304-char injection appended) |
| Latency | 2.29 s | 2.17 s |
| Response chars | 368 | 402 |
| Dream-word hits in response | 0 | 0 |

**Control opening:** *"Try checking if the file system itself is
mounted read-only ... or if SELinux/AppArmor policies are blocking
the operation..."*

**Treatment opening:** *"Step back from the file itself: check if
the *directory* containing it is readable/traversable (you need `x`
permission on parent dirs to access anything inside them)..."*

Treatment's framing shifted — "step back from the file itself" is a
meta-move, not in control. The model didn't parrot any dream content
(no dragons, no spirals, no compilers). The dream excerpts acted as
intended: as noise that knocked the response into a different local
shape without contaminating the factual layer.

## Regression test

`TestImaginationGating::test_injection_reaches_request_system_message`
drives the full `_maybe_inject` -> `call_next` path with a real
`ModelRequest` and asserts:

1. The injection header lands in `request.system_message`.
2. The base prompt is preserved (not clobbered).
3. The snapshot counter increments (`imagination_injections=1`).
4. A non-error response bumps `imagination_injections_helped=1`.

Total dreamscape tests now 43 (+1 from Phase 3), CLI total 3535.
