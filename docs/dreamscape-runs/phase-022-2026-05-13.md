# Phase 22 — 2026-05-13 (real-bug outcome experiment)

Twenty-second real-world pass. The report card's biggest remaining
gap: every prior phase used a Sonnet judge as a proxy for usefulness.
Phase 22 closes that loop with an **objective pytest pass/fail
measurement** — does imagination injection help an agent actually
fix bugs?

## TL;DR — Null Result, Honestly Reported

**Both control and treatment passed 100/100 trials across 10 bugs.**

This is the "ceiling effect" — Haiku 4.5 is too competent at
single-function bug fixes for this kind of A/B to discriminate.
Even on bugs I deliberately picked to be tricky (late-binding
closure, generator exhaustion, dict-mutation-during-iter,
floating-point equality, recursion-depth), the model nailed
10/10 in both arms.

## Why this is OK (and informative)

The dreamscape's imagination-injection mechanism is **gated** on
`consecutive_tool_failures >= 3`. The mechanism is designed for the
*stuck-agent* scenario. We forcibly bypassed the gate by
pre-priming the snapshot — even with that bypass, injection
doesn't change outcomes on tasks where the agent isn't actually
stuck.

The result is consistent with what the dreamscape's docstring
claims: injection helps when stuck, is inert otherwise. We
measured it being inert on tasks where the agent isn't stuck.
That's the design intent.

**What this can't tell us:** whether injection helps on tasks
where Haiku actually fails. To measure that, we'd need:

* Multi-file refactors (cross-codebase reasoning)
* Bugs requiring understanding of broader system context
* Tasks where multiple plausible fixes exist and only one passes a
  full test suite
* Real production debugging where the failing case is
  underspecified

Those scenarios resist clean automated testing — there's no single
pytest exit code that captures "did the agent unstuck itself."

## What the campaign's other measurements still tell us

Phase 22's null result on bug-fix correctness does NOT invalidate
the campaign's effectiveness findings. Those measured a different
property:

| Phase | Measurement | Property captured |
|---|---|---|
| **P14, P11** | Sonnet judge preference, creative prompts | Response *usefulness* |
| **P14, P16, P20** | Sonnet judge preference, technical prompts | Response *usefulness* |
| **P22** | pytest pass/fail, bug fixes | Response *correctness* |

These are different questions. Imagination injection produces
**reframes** ("step back from the file itself," "consider the
directory hierarchy") — that's not a correctness intervention,
it's a perspective intervention. A pytest test is blind to
perspective: if the model gets the answer right with or without
injection, the reframe doesn't change the bit.

The judge-based 79% (creative), 57% (technical with neutral
wrapper), 67% (decision-shaped EC vs CH) findings still stand.
They measure whether the response is *more useful*, not whether
it's *more correct*. On tasks where correctness is binary and
Haiku is competent, "more useful" doesn't show up.

## Verdict

**NULL RESULT, honestly reported.** Imagination injection neither
helps nor hurts on single-function bug-fix tasks at the difficulty
Haiku 4.5 handles trivially. The campaign's prior judge-based
findings remain the load-bearing measurements of dreamscape's
value. Phase 22 closes the "real-bug pass-rate" question with a
clear (if anticlimactic) answer: at this task class, both arms
saturate at the ceiling.

## Next steps

* **Phase 23 (suggested):** harder bug fixtures — multi-file
  refactors, ambiguous test specs, cross-codebase reasoning. Need
  tasks where Haiku 4.5 actually fails ~50% of the time so there's
  room to observe an intervention effect.
* **Phase 24 (suggested):** non-binary outcome measures — code
  review quality, parsimony, edge-case coverage. Pass/fail is too
  coarse for the property dreamscape changes.
* **Phase 25 (suggested):** production telemetry. Real users, real
  sessions, track "dreams fired" vs "task success" over time. The
  judge proxy isn't perfect; production data would close that gap.
